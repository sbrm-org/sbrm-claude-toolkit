# Documenso (SBRM e-signature)

SBRM runs its own copy of **Documenso**, an open-source e-signature platform, at **https://sign.sbrmapps.com**. It replaces paid signing services for HR and volunteer paperwork. Documents stay on SBRM-controlled infrastructure and are signed with SBRM's own certificate.

This skill is for staff *using* the service. Server administration — installing, upgrading, backups, environment config, creating accounts — is not covered here; route those to the administrator (Tim).

## Getting access

- **Self-signup is disabled.** Accounts are created by the administrator. Ask for one, and say which team you need.
- **Log in** at https://sign.sbrmapps.com/signin.
- **Documents belong to a team, not to you.** Two teams exist:

  | Team | URL slug | Membership |
  |---|---|---|
  | Human Resources | `hr` | Restricted — HR paperwork |
  | Operations | `operations` | All organisation members |

  This matters for the API: a token issued for one team cannot see the other team's documents. A 404 — or a 403 on a write call — for a document you can see perfectly well in the browser almost always means the token belongs to the wrong team.

- **Intended use** is HR and volunteer documents (roughly 250/year). It is not a general file store or a document management system.

## Create your own API key

Everyone creates and holds their own token. Tokens are not shared between people.

1. Log in at https://sign.sbrmapps.com.
2. **Decide whose documents the token should reach**, then go to the matching page:

   Every token belongs to exactly one team — that is not optional, and it is the single most common source of confusion. Create it on the team's own page:

   `https://sign.sbrmapps.com/t/<team>/settings/tokens` — e.g. `/t/hr/settings/tokens` or `/t/operations/settings/tokens`

   You can also navigate there: team switcher → **Settings** → **API Tokens**. If you need to work across both teams, you need two tokens; there is no token that sees everything.

3. Click **New token**. Give it a name describing what it is for — `volunteer-onboarding-script`, not `token1` — and choose an expiry. Prefer a real expiry over "never"; you can always mint another.
4. **Copy the token immediately.** It is displayed exactly once. If you lose it, delete it and create a new one — it cannot be retrieved later.
5. Store it in a password manager or your machine's secret store. Not in a repo, not in a chat message, not in a shared drive, not in a spreadsheet.
6. Delete tokens you are done with from the same screen.

**Working with Claude:** put the token in an environment variable (e.g. `DOCUMENSO_API_TOKEN`) and let Claude read it from the environment. Do not paste the token value into a conversation — anything typed into a chat becomes part of the transcript.

### Authenticating requests

The token goes in the `Authorization` header **as-is, with no `Bearer` prefix**. (Documenso strips a `Bearer ` prefix if you send one, so both forms work — but the bare form is what its own docs and SDKs use, so match that.)

```bash
curl -s https://sign.sbrmapps.com/api/v2/document \
  -H "Authorization: $DOCUMENSO_API_TOKEN"
```

A `401` means the header is missing, malformed, or the token is revoked/expired. If a call unexpectedly 401s, check the header format first before assuming the token is dead.

## The API

Two versions are mounted. **Use v2. Do not use v1.**

| Version | Base URL | Status |
|---|---|---|
| v2 | `https://sign.sbrmapps.com/api/v2` | Current. Use this. |
| v1 | `https://sign.sbrmapps.com/api/v1` | Deprecated upstream, **and partly broken on this instance** |

v1 is not just old. This instance stores files in its database rather than S3, and three v1 operations assume S3: creating a document, creating a template, and downloading a signed document. All three fail here. v2 does everything v1 does and more, so there is no reason to touch v1.

Machine-readable specs, worth checking before writing a call — they are generated by the running build, so they beat any external documentation:

```bash
curl -s https://sign.sbrmapps.com/api/v2/openapi.json
```

**Rate limit:** 100 requests/minute, and 20/minute for file uploads. Batch jobs need to pace themselves.

Health check (no auth needed): `curl -s https://sign.sbrmapps.com/api/health` → `{"status":"ok", ...}` including a `certificate` check. Useful first step when something seems broken.

### What you can do

| Task | v2 endpoint |
|---|---|
| Upload a PDF and create a document | `POST /document/create` (multipart) — can include recipients *and* their fields in one call |
| List / search documents | `GET /document`, `POST /document/get-many` |
| Get one document | `GET /document/{documentId}` |
| Add recipients | `POST /document/recipient/create-many` |
| Place fields | `POST /document/field/create-many` |
| Update / delete fields | `POST /document/field/update-many`, `/document/field/delete` |
| **Send for signing** | `POST /document/distribute` |
| Re-send / nudge | `POST /document/redistribute` — needs `recipients` too: an array of recipient ids, not just `documentId` |
| Cancel a sent document | `POST /envelope/cancel` |
| Download the PDF | `GET /document/{documentId}/download?version=signed` (or `original`) — returns raw PDF bytes |
| Download the signing certificate | `GET /envelope/{envelopeId}/certificate/download` |
| Download the audit log | `GET /envelope/{envelopeId}/audit-log/download` |
| List templates | `GET /template`, `POST /template/get-many` |
| **Create a document from a template** | `POST /template/use` |
| Folders | `GET /folder`, `POST /folder/create` |

Documents also surface as **envelopes** (`/envelope/*`) — the newer container model that can hold more than one file. **Cancel, certificate download, and audit-log download exist only on the envelope routes, and they key off the string `envelopeId`, not the numeric `documentId`** used everywhere else. Every document response (`POST /document/create`, `GET /document/{documentId}`, `POST /template/use`) includes `envelopeId` — capture it and keep it, because the moment you need it is the moment you have mis-sent something:

```bash
curl -s -X POST https://sign.sbrmapps.com/api/v2/envelope/cancel \
  -H "Authorization: $DOCUMENSO_API_TOKEN" -H "Content-Type: application/json" \
  -d '{"envelopeId":"<envelopeId>","reason":"wrong recipient"}'
```

### Field types and positioning

`POST /document/field/create-many` takes `documentId` and a `fields` array. Every field needs:

| Property | Meaning |
|---|---|
| `recipientId` | Who fills it — from the recipient you created |
| `pageNumber` | 1-based page |
| `pageX`, `pageY` | Top-left corner, as a **percentage of page width/height** |
| `width`, `height` | Size, also as percentages (minimum 1) |
| `type` | One of the types below |
| `fieldMeta` | Optional — but if you include it, it must carry its **own lowercase `type`** matching the field (`"type":"SIGNATURE"` → `fieldMeta:{"type":"signature", ...}`), or validation fails. Common keys: `label`, `placeholder`, `required`, `readOnly`, `fontSize` (8–96), `overflow`. `textAlign` exists only on `INITIALS`, `NAME`, `EMAIL`, `DATE`, `TEXT`, `NUMBER` — not on `SIGNATURE`, `RADIO`, `CHECKBOX`, or `DROPDOWN`; `FREE_SIGNATURE` takes no `fieldMeta` at all. Text and choice types add their own (`characterLimit`, `minValue`/`maxValue`, `values`, `defaultValue`) — check the spec. |

Types: `SIGNATURE`, `FREE_SIGNATURE`, `INITIALS`, `NAME`, `EMAIL`, `DATE`, `TEXT`, `NUMBER`, `RADIO`, `CHECKBOX`, `DROPDOWN`.

Coordinates behave as percentages of the page — `pageX: 10, pageY: 80` places a field 10% from the left and 80% down — but **the API neither documents nor validates the units.** The schema enforces only `pageX`/`pageY` ≥ 0 and `width`/`height` ≥ 1, with **no upper bound**. `pageX: 400` is accepted, returns `200`, and puts the field off the page. Nothing will tell you.

So: **open the draft in the browser and look at it before distributing.** Arithmetic alone is not verification here. And if you are placing fields on the same form repeatedly, place them once in the UI and save it as a **template** — that is what templates are for.

These property names are **v2 only**. Deprecated v1 used `pageWidth`/`pageHeight` instead of `width`/`height`, on a different path shape. If you find an old snippet using `pageWidth`, it is v1 — do not paste it into a v2 call.

One more naming quirk, so it doesn't alarm you: the *response* from `field/create-many` reports positions as `page`, `positionX`, `positionY` — different names from the `pageNumber`, `pageX`, `pageY` you sent. That is cosmetic. Your write did take.

### Recipient roles

`SIGNER` (signs), `APPROVER` (approves), `VIEWER` (read-only), `CC` (gets a copy), `ASSISTANT` (fills fields for others).

**Signing order is set on the document, not on distribute.** Pass `meta.signingOrder: "SEQUENTIAL"` in the `payload` of `POST /document/create` (or later via `POST /document/update`), and give each recipient a numeric `signingOrder`. `POST /document/distribute` has no `signingOrder` field — put it there and it is **silently ignored**, and your carefully ordered HR packet goes out to everyone at once with no error. Default is `PARALLEL`.

## Recipes

### Send an existing template

Best path for repeating paperwork. Build the template once in the UI with the fields already placed, then:

```bash
# 1. Find the template
curl -s https://sign.sbrmapps.com/api/v2/template \
  -H "Authorization: $DOCUMENSO_API_TOKEN"

# 2. Create a document from it, prefilled — but do NOT send yet
curl -s -X POST https://sign.sbrmapps.com/api/v2/template/use \
  -H "Authorization: $DOCUMENSO_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "templateId": 12,
        "recipients": [{"id": 1, "name": "Jane Doe", "email": "jdoe@example.org"}],
        "distributeDocument": false
      }'
```

`recipients[].id` is the **template recipient's** id (the placeholder role in the template), not a person's id. Get it from `GET /template/{templateId}`.

Setting `distributeDocument: true` sends immediately. Leave it `false`, review the draft, then distribute deliberately.

### Upload a PDF, place fields, send

```bash
# 1. Upload the file and create the document
curl -s -X POST https://sign.sbrmapps.com/api/v2/document/create \
  -H "Authorization: $DOCUMENSO_API_TOKEN" \
  -F 'payload={"title":"Volunteer Agreement - Jane Doe"};type=application/json' \
  -F "file=@/path/to/agreement.pdf;type=application/pdf"
# -> {"id": 123, "envelopeId": "..."}

# 2. Add the signer
curl -s -X POST https://sign.sbrmapps.com/api/v2/document/recipient/create-many \
  -H "Authorization: $DOCUMENSO_API_TOKEN" -H "Content-Type: application/json" \
  -d '{"documentId":123,"recipients":[{"name":"Jane Doe","email":"jdoe@example.org","role":"SIGNER"}]}'
# -> recipient id, e.g. 456

# 3. Place a signature and a date field on page 1
curl -s -X POST https://sign.sbrmapps.com/api/v2/document/field/create-many \
  -H "Authorization: $DOCUMENSO_API_TOKEN" -H "Content-Type: application/json" \
  -d '{"documentId":123,"fields":[
        {"recipientId":456,"type":"SIGNATURE","pageNumber":1,"pageX":10,"pageY":80,"width":25,"height":6},
        {"recipientId":456,"type":"DATE","pageNumber":1,"pageX":60,"pageY":80,"width":20,"height":5}
      ]}'

# 4. Look at the draft in the browser. Then, and only then:
curl -s -X POST https://sign.sbrmapps.com/api/v2/document/distribute \
  -H "Authorization: $DOCUMENSO_API_TOKEN" -H "Content-Type: application/json" \
  -d '{"documentId":123,"meta":{"subject":"Please sign your volunteer agreement"}}'
```

### Check status and collect the signed file

```bash
curl -s "https://sign.sbrmapps.com/api/v2/document/123" -H "Authorization: $DOCUMENSO_API_TOKEN"
```

Look at the document `status` and each recipient's signing status to see who is outstanding. Once complete:

```bash
# These return raw PDF bytes — always redirect to a file, or you dump binary into your terminal
curl -s -o signed.pdf "https://sign.sbrmapps.com/api/v2/document/123/download?version=signed" \
  -H "Authorization: $DOCUMENSO_API_TOKEN"

curl -s -o certificate.pdf "https://sign.sbrmapps.com/api/v2/envelope/<envelopeId>/certificate/download" \
  -H "Authorization: $DOCUMENSO_API_TOKEN"
```

The **certificate** is the evidence record — who signed, when, from where. For anything that might be disputed, keep it with the signed PDF.

## Webhooks

Documenso can POST to a URL of your choosing when something happens to a document. This is how you build "when it's signed, file it somewhere" automation without polling.

Webhooks are **team-only** and configured **in the UI only** — there is no API for creating or managing them:

`https://sign.sbrmapps.com/t/<team>/settings/webhooks`

A webhook has a target URL, a set of event triggers, an optional **secret**, and an enabled flag. The dialog has a **Test** button that fires sample data — use it before wiring anything downstream.

Events this instance can emit:

| Group | Events |
|---|---|
| Document lifecycle | `DOCUMENT_CREATED`, `DOCUMENT_SENT`, `DOCUMENT_OPENED`, `DOCUMENT_SIGNED`, `DOCUMENT_COMPLETED`, `DOCUMENT_REJECTED`, `DOCUMENT_CANCELLED` |
| Recipients | `DOCUMENT_RECIPIENT_COMPLETED`, `DOCUMENT_REMINDER_SENT`, `RECIPIENT_EXPIRED` |
| Templates | `TEMPLATE_CREATED`, `TEMPLATE_UPDATED`, `TEMPLATE_DELETED`, `TEMPLATE_USED` |

`DOCUMENT_COMPLETED` — everyone has signed — is the one that matters for downstream automation. `DOCUMENT_SIGNED` fires per signature, so on a multi-signer document it fires more than once; do not treat it as "finished".

**Verifying the sender.** Documenso sends your configured secret verbatim in an `X-Documenso-Secret` header. That is a shared password, not a signed digest — there is no HMAC, no timestamp, no replay protection. So: always set a secret, always compare it constant-time, and **the receiving URL must be HTTPS**, or the secret travels in the clear.

**Delivery.** 10-second timeout per attempt, retried up to 3 times, redirects not followed. Every attempt is logged with the response code and body, so when a webhook "doesn't fire", check that log first — a 500 from *your* endpoint looks identical to silence from the outside.

**Private addresses are refused.** Documenso resolves the webhook URL and rejects anything landing on a private or loopback address. A URL pointing at a LAN host, a Tailscale `100.x` address, or `localhost` will not be accepted. The receiver has to be reachable on the public internet.

**Payloads** carry document and recipient state including both `id` (numeric document id) and `envelopeId` — enough to then fetch the signed PDF and the certificate. Still treat the webhook as a **notification, not a data source**: on receipt, call the API for authoritative state rather than trusting the payload.

## Safety rules

1. **Never send a document for signature without an explicit go-ahead from the person who owns the task.** Distribution emails real people and cannot be un-sent; the most you can do afterwards is cancel and apologise. Draft, show the draft, then send as a separate step.
2. **Check the recipient email before distributing.** A typo'd address silently delivers confidential paperwork to a stranger. Read the address back before sending.
3. **Never share, paste, or commit a token.** If one leaks, delete it on the tokens page immediately and mint a new one.
4. **Do not delete documents.** Completed documents are records. To stop something in flight, cancel it (`POST /envelope/cancel`) — the UI gives you no way to undo a delete.
5. **Stay in your team.** If a call 404s, you are probably using the wrong team's token. Do not go looking for a broader-scoped one.
6. **Test with a throwaway document.** Field coordinates, signing order, and template recipient ids are all easy to get wrong. Send a test to yourself before a batch of real ones.
7. **Verify before reporting done.** "Sent" means the API returned success *and* the document status reflects it. Show the status output rather than asserting it.
